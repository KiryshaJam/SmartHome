# Проверка интерфейса спецификаций

Только отдельная одноразовая PostgreSQL и API с явным тестовым подключением.
Основная БД и ручная playground для проверок с записью не используются.
Для работы с уже запущенным GUI использовать его отдельный адрес, а не основной
демонстрационный запуск. Созданные тестовые изделия и заказы не переносить в main.

## Основной сценарий без технических обозначений

1. В «Изделия» создать материал в классе кабелей. Его собственный состав пока
   не настраивать. Создать сборку с числом датчиков и типом подключения.
2. На шаге «1. Параметры изделия» задать диапазон числа 1..4 и исходное значение 2.
   Для перечисления оставить проводное/беспроводное подключение, выбрать исходное.
   Нажать «Сохранить параметры → к компонентам»: открывается шаг 2 без отдельного
   обязательного комментария. История получает описание изменения автоматически.
3. Добавить материал. Если он ещё не настроен, отметить использование без вложенных
   компонентов и выбрать метр. Не требуется переходить в другую карточку.
4. В условии включения выбрать «Задать условие», параметр «Тип подключения»,
   сравнение «равно», значение «Проводное подключение».
   В формуле выбрать расчёт по параметрам: «Число датчиков», «умножить на», 2.
   Закончить компонент и сохранить состав: открывается шаг 3.
5. Проверить 2 датчика/проводное: 4 м; 3/проводное: 6 м; беспроводное: материала нет.
   Значение 8 отклоняется с названием параметра. Ни в полях, ни в результате не
   требуется вводить служебные ключи, кавычки или английские коды подключения.
6. Сохранить два исполнения. Пустое название допустимо: создаётся понятное имя.
   В раскрываемом разделе готовых исполнений открыть параметры сохранённого,
   рассчитать всю глубину и общий расход для количества изделий/класса материалов.
7. В заказах выбрать исполнения 4 м × 3 и 6 м × 2: итог 24 м. Сохранение автоматически
   рассчитывает расход. Через встроенный подбор также создать исполнение без имени,
   добавить его и сохранить. Полный состав строки соответствует выбранному исполнению.
8. Изменить формулу шаблона через поля на множитель 3. Новые исполнения используют
   новую норму, прежние исполнения и заказ сохраняют исходные значения. После reload
   повторно открыть заказ, сверить прежние 24 м.

## Параметры и сложные возможности

- Подключение из справочника показывает список с пустыми отметками. Подключаются
  только отмеченные параметры. Отмена ничего не добавляет. Из параметров можно
  убрать неиспользуемый, а затем вернуть через этот список; справочник не меняется.
  Параметр, задействованный в вычислениях/условиях/передачах, убрать нельзя, пока
  его использование не удалено. После удаления/перевода параметра в вычисляемый
  старые значения его ввода не отправляются конфигуратору.
- Подключить вычисляемую длину линии и задать её через поля: число датчиков × 2.
  В поле результата типа «Число» можно использовать исходный параметр «Целое число».
  Длина отсутствует среди полей ввода исполнения, но показана в результате.
- Создать правило с двумя условиями. Переключение «все» ↔ «хотя бы одно» меняет
  только связь условий, не добавляет нового условия. Проводное ИЛИ беспроводное
  проходит, гибридное отклоняется с заданным текстом отказа. Проверить запрет
  сочетания и добавление/удаление вложенных условий.
- Быстрая совместимость: выбрать два компонента и запрет совместного использования;
  при включении обоих проверка отклоняет конфигурацию с названиями компонентов.
  Также проверить требование второго компонента при наличии первого.
- Создать модификацию. Проверить унаследованную/заменённую/собственную позиции,
  исключение и возврат, а также возврат замены к базе. Базовое изделие не меняется.
- В дополнительном разделе компонента выбрать передачу значений. Для числа
  датчиков дочерней сборки выбрать одноимённый параметр родителя. Одинаковые
  определения на разных уровнях допускаются. Проверить расчёт на всей глубине.
  Затем выбрать готовое дочернее исполнение: его параметры не зависят от новых
  значений родителя. Переключение способа очищает несовместимые настройки передачи.
- В истории прежние условия и формулы читаются по названиям, старые ограничения
  остаются прежними. Исторические поля и сохранение недоступны для изменения.
  Возврат к текущей версии не теряет её черновые правки.
- Дополнительный режим показывает точный исходный текст сохранённого выражения.
  Открытие/закрытие, фокус и Tab без правок не меняют текст и не помечают форму
  изменённой. Свободный ввод остаётся доступным для сложных случаев. Строковые
  литералы не подменяются именами параметров; скобки/приоритеты сохраняются.

## Состояние формы и доступность

- Редактор компонента заменяет список на том же месте. «Готово» возвращает список,
  а сохранение шага применяется ко всему составу. Пока редактор открыт, сохранение
  всей спецификации недоступно. Случайный переход с правками требует подтверждения.
- После изменения параметров проверки прежние подтверждение и таблица исчезают.
  Изменение количества/класса готового исполнения очищает дерево и расход.
- Правки заказа скрывают сохранённый расход до следующего сохранения; при смене
  заказа/класса запоздалый результат не подставляется в новую форму.
- Открыть старый заказ и нажать «Новый»: дата становится сегодняшней.
- До расчёта нет сообщения о пустом классе; успешный пустой результат показывает его.
  При ошибке расчёта заказа доступна кнопка повтора.
- Поиск в каталоге находит изделие по названию, обозначению или классу.
- Проверить 390 px: вся страница не прокручивается горизонтально; таблицы имеют
  внутреннюю прокрутку, поля условий/формул переносятся в столбец.
  Выбор изделия на узком экране ведёт к карточке; возврат к списку не стирает форму.
- Проверить Tab, сообщения ошибок без служебных ключей и консоль React.

Автономные проверки выражений без БД: `npm --prefix smart-home-web run test:expressions`.
Результат реального GUI-прогона фиксировать отдельно от этого сценария. Проверки
с искусственной задержкой/обрывом сети и перезапуском стенда отмечать отдельно,
не считать их выполненными только по открытию страницы.
