# Проверка спецификаций через интерфейс

Только отдельная тестовая PostgreSQL; запустить API с явным тестовым подключением.
Фикстуры `api_bom.py --allow-test-writes` создают класс материалов с подклассом,
класс сборок и параметры числа датчиков/подключения. Можно использовать эти классы
или создать аналогичные в классификаторе и справочниках.

1. В «Изделиях» создать кабель в классе материалов. Задать единицу «метр»,
   причину и сохранить пустую спецификацию. Создать комплект в классе сборок,
   задать единицу «комплект».
2. Добавить кабель, расход 1, для количества 1. Задать условие `pN == "wired"`
   (N — ID строкового параметра подключения), формулу `pK * 2` (K — ID числа
   датчиков). Добавить ограничение `pK <= 4 AND (pN == "wired" OR pN == "radio")`
   с понятным сообщением отказа. Сохранить с причиной.
3. Сохранить два варианта: wired/2 и wired/3. Первый должен давать 4 м, второй
   6 м. Конфигурация wired/8 должна отклоняться и не появляться в списке вариантов.
4. Создать модификацию. В ней заменить компонент, добавить ещё одну позицию,
   исключить унаследованную и вернуть её. Сохранить. Состав базы не меняется.
   Проверить разные позиции с одним и тем же компонентом.
5. Включить конфигурируемую сборку внутрь комплекта. В полях передачи параметров
   задать выражения параметров родителя. Сохранить новый вариант, проверить
   условия и формулы у дочерней сборки. Отдельно выбрать сохранённый дочерний
   вариант и проверить его собственную конфигурацию.
6. В «Заказах» создать заказ, выбрать wired/2 × 3 и wired/3 × 2. Сохранить.
   Полный состав каждой позиции должен соответствовать её варианту, общий расход
   кабеля — 24 м. Выбор класса материалов включает его подклассы; единицы не смешиваются.
7. В заказе создать вариант через встроенную форму, добавить его в позиции,
   изменить количество и сохранить новую версию. История заказа содержит прежние
   позиции; их состав и расход доступны отдельно.
8. Изменить условие/формулу исходного комплекта, сохранить. Новая конфигурация
   использует новую версию, старые варианты и заказ всё ещё дают прежние нормы.
   В истории спецификации открыть прежнюю версию, сравнить позиции и правила.
9. Обновить страницу, заново открыть заказ. Перезапустить только тестовый API
   и PostgreSQL. Сверить состав и 24 м исходной версии заказа после перезапуска.
10. Проверить ширину 390 px, прокрутку таблиц внутри карточки, ввод с клавиатуры,
    сообщения ошибок и отсутствие ошибок/предупреждений React в консоли.
