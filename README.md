# SmartHome

Справочник систем умного дома: классификатор, перечисления, параметры и карточки изделий.

## Запуск

Требуются .NET SDK 10, Node.js/npm, PostgreSQL 17 (или Docker Desktop), `dotnet ef`.

1. Запустите PostgreSQL: `docker compose -f SmartHome/docker-compose.yml up -d`.
2. Задайте подключение через `ConnectionStrings__DefaultConnection` или локальную конфигурацию ASP.NET. Перед обновлением существующей базы сохраните `pg_dump` вне репозитория. Для восстановления используйте `pg_restore` в отдельную базу и переключите подключение после проверки.
3. Выполните `dotnet ef database update --project SmartHome`. Миграции устанавливают схему, начальные данные и SQL-функции; отдельно запускать SQL-файлы не нужно.
4. Запустите API: `dotnet run --project SmartHome --launch-profile http` (порт 5156, Swagger: `/swagger`).
5. Выполните `npm --prefix smart-home-web ci`, затем `npm --prefix smart-home-web run dev -- --host 127.0.0.1 --port 5173 --strictPort`.
6. Откройте http://127.0.0.1:5173. Запросы `/api` передаются через Vite на API.

Для собранного интерфейса: `npm --prefix smart-home-web run build`, затем `npm --prefix smart-home-web run preview -- --host 127.0.0.1 --port 4173 --strictPort`. API по умолчанию находится на http://localhost:5156; другой адрес задаётся переменной `VITE_API_URL` **при сборке**. CORS разрешает только указанные локальные адреса на портах 3000, 4173, 5173. При размещении на сервере настройте точный origin и HTTPS.

Не запускайте изменяющие данные тесты на рабочей базе. Используйте отдельную PostgreSQL и явно задавайте тестовое подключение.

## Наследование параметров

Новый класс получает копии параметров родителя; новый параметр автоматически распространяется вниз по дереву в той же транзакции. Совпадение определения сохраняет существующую локальную привязку и её ограничения. При переносе класса добавляются недостающие параметры нового родителя, прежние настройки и значения сохраняются. Изменения настроек родителя не перезаписывают уже созданные копии: это снимок настроек на момент наследования. Повторное копирование безопасно.

## Карточки, перенос и ограничения

Изделие создаётся сразу, значения параметров сохраняются по одному. Отдельных статусов и завершения карточки нет. Обязательные параметры отмечены в форме: после заполнения их нельзя очистить, но можно заменить допустимым значением. Новый обязательный параметр можно добавить к классу с существующими изделиями и затем заполнить в их карточках. Неполное заполнение не скрывает изделие из справочника или поиска.

Изделия размещаются только в конечных классах; конечный класс не может иметь потомков. Перенос сопоставляет определения параметров и сохраняет значения атомарно. Если целевой класс не содержит параметр с сохранённым значением или имеет несовместимые ограничения, перенос отклоняется. Изменение ограничений параметра проверяет существующие значения.

Даты API: ISO 8601 с `Z` или явным смещением (`2026-01-01T12:00:00+03:00`), хранение в UTC. Даты без пояса отклоняются. Интерфейс вводит местное время и преобразует его в UTC. Строковое значение — до 1024 символов. Для SQL-параметров `timestamptz` передавайте явное смещение; PostgreSQL преобразует его в UTC.

Порядок значений перечисления меняется атомарным обменом позиций. Используемое значение нельзя удалить или изменить его смысл; добавьте новый вариант. Имя иконки отображается символом: `lightbulb`, `thermostat`, `camera`, `plug`, `lock`, `home`; неизвестные имена имеют нейтральный значок и подпись.

Проверки типов, связей, диапазонов и терминальности находятся в PostgreSQL и применяются к API и прямому SQL. Триггеры сериализуют изменения каталога транзакционной блокировкой; чтение остаётся параллельным. API дополнительно проверяет формат запроса и возвращает 400/409 для ошибок данных. Миграция ограничений проверяет старые данные и останавливается при противоречиях; ничего автоматически не удаляет.

## SQL-интерфейс

| Область | Функции |
| --- | --- |
| Дерево классов | `add_class_node`, `delete_class_node`, `move_class_node`, `update_class_sort_order`, `find_children`, `find_parents`, `find_leaves_by_class` |
| Изделия | `add_product`, `delete_product`, `move_product`, `get_products_by_class` |
| Перечисления | `get_enum_classes`, `add_enum_class`, `delete_enum_class`, `update_enum_class_sort_order`, `get_enum_values`, `add_enum_value`, `delete_enum_value`, `is_enum_value_allowed`, `update_enum_value_sort_order` |
| Параметры | `describe_parameter`, `bind_class_parameter`, `update_class_parameter`, `inherit_class_parameters`, `get_class_parameters` |
| Значения и поиск | `write_product_parameter`, `get_product_parameters`, `group_product_parameters`, `filter_products` |

Миграция `RemoveProductDraftStatus` удаляет только прежний статус изделия и связанные с ним правила, сохраняя изделия и все значения. Перед обновлением существующей базы сохраните резервную копию. Автоматический откат этой миграции запрещён: прежние статусы восстанавливаются только из копии в отдельную БД.

Версии SQL зафиксированы в миграциях. Файлы `SmartHome/Sql` представляют текущие определения операций. При изменении SQL создавайте новую миграцию, не меняйте уже развёрнутые версии.

## Проверки на отдельной базе

1. Создайте PostgreSQL 17 на отдельном свободном порту, например 55433, с отдельной БД `smarthome_review`.
2. Примените миграции с явным тестовым подключением: `dotnet ef database update --project SmartHome --connection 'Host=127.0.0.1;Port=55433;Database=smarthome_review;Username=postgres;Password=TEST_PASSWORD'`.
3. Выполните `tests/deployment.sql`, `tests/inheritance.sql`, `tests/integrity.sql` через `psql -v ON_ERROR_STOP=1`. SQL-тесты откатывают изменения.
4. Запустите API на 5156 с переменной `ConnectionStrings__DefaultConnection`, указывающей **только на тестовую базу**.
5. Выполните `python3 tests/api_integrity.py --allow-test-writes`, `python3 tests/api_catalog.py --allow-test-writes` и `python3 tests/api_concurrency.py --allow-test-writes`. Они включают поиск по пяти типам. HTTP-тесты создают записи с уникальным префиксом в тестовой базе; используйте новую базу для чистого прогона.
6. Для проверки обновления без потери данных в отдельной базе примените миграции до `20260926073100_AddCatalogOperations`. Выполните `tests/draft_removal_upgrade.sql` через `psql -v ON_ERROR_STOP=1 -v before=1`, примените оставшиеся миграции и повторите файл с `-v before=0`. Проверка сравнивает полное содержимое девяти таблиц, включая заполненные и незаполненные изделия, покрывающие оба прежних статуса.
7. Проверьте сборки `dotnet build SmartHome` и `npm --prefix smart-home-web run build`.

Проверка интерфейса в dev и preview:

- В справочниках создайте строковое перечисление и два варианта; поменяйте их порядок.
- Создайте параметр этого перечисления, привяжите его как обязательный к промежуточному классу. После этого создайте конечного потомка.
- Создайте устройство в потомке. Параметр должен появиться автоматически с отметками наследования и обязательности.
- Сохраните вариант обязательного параметра, измените его и убедитесь, что кнопки сброса у него нет. Статусов и отдельного завершения карточки быть не должно.
- В поиске выберите родителя и вариант параметра, найдите устройство и откройте его по названию.
- В настройках параметра потомка измените группу и порядок. Проверьте сохранность значения в карточке, в том числе после обновления страницы и перезапуска тестовой PostgreSQL.
- Проверьте быстрый выбор разных устройств и классов, работу кнопок с клавиатуры и ширину 390 пикселей. Недоступный сервер или база должны показывать понятное сообщение без технического стека.
