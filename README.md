# SmartHome

Справочник систем умного дома: классификатор, перечисления, параметры и карточки изделий.

## Запуск

Требуются .NET SDK 10, Node.js/npm, PostgreSQL 17 (или Docker Desktop), `dotnet ef`.

1. Запустите PostgreSQL: `docker compose -f SmartHome/docker-compose.yml up -d`.
2. Задайте подключение через `ConnectionStrings__DefaultConnection` или локальную конфигурацию ASP.NET. Перед обновлением существующей базы сохраните `pg_dump` вне репозитория. Для восстановления используйте `pg_restore` в отдельную базу и переключите подключение после проверки.
3. Выполните `dotnet ef database update --project SmartHome`. Миграции устанавливают схему, начальные данные и SQL-функции; отдельно запускать SQL-файлы не нужно.
4. Запустите API: `dotnet run --project SmartHome --launch-profile http` (порт 5156, Swagger: `/swagger`).
5. Выполните `npm --prefix smart-home-web ci`, затем `npm --prefix smart-home-web run dev -- --host 127.0.0.1 --port 5173 --strictPort`.
6. Откройте http://127.0.0.1:5173. Запросы `/api` передаются через Vite на API.

Для собранного интерфейса: `npm --prefix smart-home-web run build`, затем `npm --prefix smart-home-web run preview -- --host 127.0.0.1 --port 4173 --strictPort`. API по умолчанию находится на http://localhost:5156; другой адрес задаётся переменной `VITE_API_URL` **при сборке**. CORS разрешает только указанные локальные адреса на портах 3000, 4173, 5173. При размещении на сервере настройте точный origin и HTTPS.

Не запускайте изменяющие данные тесты на рабочей базе. Используйте отдельную PostgreSQL и явно задавайте тестовое подключение.

## Наследование параметров

Новый класс получает копии параметров родителя; новый параметр автоматически распространяется вниз по дереву в той же транзакции. Совпадение определения сохраняет существующую локальную привязку и её ограничения. При переносе класса добавляются недостающие параметры нового родителя, прежние настройки и значения сохраняются. Изменения настроек родителя не перезаписывают уже созданные копии: это снимок настроек на момент наследования. Повторное копирование безопасно.

## Карточки, перенос и ограничения

Изделие создаётся сразу, значения параметров сохраняются по одному. Отдельных статусов и завершения карточки нет. Обязательные параметры отмечены в форме: после заполнения их нельзя очистить, но можно заменить допустимым значением. Новый обязательный параметр можно добавить к классу с существующими изделиями и затем заполнить в их карточках. Неполное заполнение не скрывает изделие из справочника или поиска.

Изделия размещаются только в конечных классах; конечный класс не может иметь потомков. Перенос сопоставляет определения параметров и сохраняет значения атомарно. Если целевой класс не содержит параметр с сохранённым значением или имеет несовместимые ограничения, перенос отклоняется. Изменение ограничений параметра проверяет существующие значения.

Даты API: ISO 8601 с `Z` или явным смещением (`2026-01-01T12:00:00+03:00`), хранение в UTC. Даты без пояса отклоняются. Интерфейс вводит местное время и преобразует его в UTC. Строковое значение — до 1024 символов. Для SQL-параметров `timestamptz` передавайте явное смещение; PostgreSQL преобразует его в UTC.

Порядок значений перечисления меняется атомарным обменом позиций. Используемое значение нельзя удалить или изменить его смысл; добавьте новый вариант. Имя иконки отображается символом: `lightbulb`, `thermostat`, `camera`, `plug`, `lock`, `home`; неизвестные имена имеют нейтральный значок и подпись.

Проверки типов, связей, диапазонов и терминальности находятся в PostgreSQL и применяются к API и прямому SQL. Триггеры сериализуют изменения каталога транзакционной блокировкой; чтение остаётся параллельным. API дополнительно проверяет формат запроса и возвращает 400/409 для ошибок данных. Миграция ограничений проверяет старые данные и останавливается при противоречиях; ничего автоматически не удаляет.

## SQL-интерфейс

| Область | Функции |
| --- | --- |
| Дерево классов | `add_class_node`, `delete_class_node`, `move_class_node`, `update_class_sort_order`, `find_children`, `find_parents`, `find_leaves_by_class` |
| Изделия | `add_product`, `delete_product`, `move_product`, `get_products_by_class` |
| Перечисления | `get_enum_classes`, `add_enum_class`, `delete_enum_class`, `update_enum_class_sort_order`, `get_enum_values`, `add_enum_value`, `delete_enum_value`, `is_enum_value_allowed`, `update_enum_value_sort_order` |
| Параметры | `describe_parameter`, `bind_class_parameter`, `update_class_parameter`, `inherit_class_parameters`, `get_class_parameters` |
| Значения и поиск | `write_product_parameter`, `get_product_parameters`, `group_product_parameters`, `filter_products` |

Миграция `RemoveProductDraftStatus` удаляет только прежний статус изделия и связанные с ним правила, сохраняя изделия и все значения. Перед обновлением существующей базы сохраните резервную копию. Автоматический откат этой миграции запрещён: прежние статусы восстанавливаются только из копии в отдельную БД.

Версии SQL зафиксированы в миграциях. Файлы `SmartHome/Sql` представляют текущие определения операций. При изменении SQL создавайте новую миграцию, не меняйте уже развёрнутые версии.

## Проверки на отдельной базе

1. Создайте PostgreSQL 17 на отдельном свободном порту, например 55433, с отдельной БД `smarthome_review`.
2. Примените миграции с явным тестовым подключением: `dotnet ef database update --project SmartHome --connection 'Host=127.0.0.1;Port=55433;Database=smarthome_review;Username=postgres;Password=TEST_PASSWORD'`.
3. Выполните `tests/deployment.sql`, `tests/inheritance.sql`, `tests/integrity.sql` через `psql -v ON_ERROR_STOP=1`. SQL-тесты откатывают изменения.
4. Запустите API на 5156 с переменной `ConnectionStrings__DefaultConnection`, указывающей **только на тестовую базу**.
5. Выполните `python3 tests/api_integrity.py --allow-test-writes`, `python3 tests/api_catalog.py --allow-test-writes` и `python3 tests/api_concurrency.py --allow-test-writes`. Они включают поиск по пяти типам. HTTP-тесты создают записи с уникальным префиксом в тестовой базе; используйте новую базу для чистого прогона.
6. Для проверки обновления без потери данных в отдельной базе примените миграции до `20260926073100_AddCatalogOperations`. Выполните `tests/draft_removal_upgrade.sql` через `psql -v ON_ERROR_STOP=1 -v before=1`, примените оставшиеся миграции и повторите файл с `-v before=0`. Проверка сравнивает полное содержимое девяти таблиц, включая заполненные и незаполненные изделия, покрывающие оба прежних статуса.
7. Проверьте сборки `dotnet build SmartHome` и `npm --prefix smart-home-web run build`.

Проверка интерфейса в dev и preview:

- В справочниках создайте строковое перечисление и два варианта; поменяйте их порядок.
- Создайте параметр этого перечисления, привяжите его как обязательный к промежуточному классу. После этого создайте конечного потомка.
- Создайте устройство в потомке. Параметр должен появиться автоматически с отметками наследования и обязательности.
- Сохраните вариант обязательного параметра, измените его и убедитесь, что кнопки сброса у него нет. Статусов и отдельного завершения карточки быть не должно.
- В поиске выберите родителя и вариант параметра, найдите устройство и откройте его по названию.
- В настройках параметра потомка измените группу и порядок. Проверьте сохранность значения в карточке, в том числе после обновления страницы и перезапуска тестовой PostgreSQL.
- Проверьте быстрый выбор разных устройств и классов, работу кнопок с клавиатуры и ширину 390 пикселей. Недоступный сервер или база должны показывать понятное сообщение без технического стека.

## Спецификации, конфигурации и заказы

EF Core Code First и миграции управляют схемой PostgreSQL. BOM использует восемь
таблиц: `bom_revision`, `bom_position`, `bom_parameter`, `bom_parameter_option`,
`bom_position_binding`, `bom_rule`, `bom_order`, `bom_order_line`.
Справочник изделий и его девять таблиц сохраняются.

В `bom_revision` находятся версии шаблонов и конкретные исполнения, различаемые
флагом `IsConfigured`. История шаблонов использует `PreviousId`; модификация
закрепляет `BaseRevisionId` и хранит только добавления, замены и исключения позиций
по постоянному ключу. Базовый состав читается из базовой версии. Изменение шаблона
создаёт новую версию и не изменяет прежние исполнения.

Параметры и их числовые ограничения находятся в `bom_parameter`; допустимые
значения перечисления конкретного параметра связаны через `bom_parameter_option`
с существующим справочником. Формула вычисляемого параметра хранится в его строке.
В выражениях используются ключи `p12`, арифметика, сравнения, `AND`, `OR`, `NOT`,
строковые константы и проверки компонентов `has_8`. У позиции есть условие включения,
формула расхода и норма «расход / для количества». Нулевые знаменатели запрещены.

Вложенный шаблон получает значения через `bom_position_binding`; также можно
выбрать уже готовое дочернее исполнение. Существующий ограниченный интерпретатор
проверяет типы, диапазоны, перечисления, условия и совместимость на каждом уровне.
Всё дерево сохраняется одной транзакцией. Исполнения хранят фиксированный состав,
выбранные и вычисленные значения в тех же связанных таблицах; при последующем
расчёте выражения не исполняются. Относительная норма `ResolvedQuantity` сохраняет
прежний точный decimal-результат деления, а `Amount/ForQuantity` — исходную норму.
Даты параметров хранятся как целочисленные .NET ticks для сохранения точности 100 нс.
JSON применяется только для обмена с API и SQL-функциями, без JSON-колонок в модели.

Заказ содержит номер, дату и строки «исполнение + количество». Можно создать
исполнение из формы заказа. Редактирование атомарно заменяет текущие строки;
`UpdateToken` защищает от одновременной перезаписи. Отдельной истории заказов нет.
При переходе старые версии заказов должны сохраняться в проверенном исходном архиве;
миграция переносит в рабочую модель последний состав каждого существующего заказа.
Имена изделий, классы и подписи перечислений отображаются по текущему каталогу.
Фиксированные состав, нормы и значения исполнений от изменения подписей не зависят.

В карточке «Изделия» настройка проходит по трём шагам: «Параметры изделия»,
«Компоненты и расход», «Проверка и исполнение». Сохранение ведёт к следующему шагу;
комментарий к изменению необязателен, без него сохраняется описание выполненного шага.
Условия и формулы задаются выбором названий, операций и значений. Например:
«Тип подключения равно Проводное подключение», «Число датчиков умножить на 2».
Технические обозначения не требуются в обычном режиме. Текст исходного выражения
доступен в дополнительных настройках; открытие формы его не переписывает.
Составные условия поддерживают «все», «хотя бы одно» и запрет сочетания.

При подключении параметров справочника пользователь отмечает только нужные.
Неиспользуемый параметр можно убрать из настройки, сохранив его в справочнике;
параметр, задействованный в условиях/формулах, сначала нужно освободить от ссылок.
Для нового материала единицу можно задать непосредственно при включении в состав,
без перехода в его карточку. Вложенный состав и передачи параметров доступны
в дополнительных настройках компонента. История и модификации вынесены отдельно.

Проверка показывает весь состав и фактические значения, включая вычисленные.
Исполнение можно сохранить без собственного названия: оно создаётся автоматически.
В заказе расход рассчитывается после сохранения и выбора класса; при правках
предыдущий результат скрывается. Несохранённые настройки защищены от случайного
перехода. Каталог имеет поиск по названию/классу; на узком экране выбор изделия
переводит к его карточке, откуда можно вернуться к списку.

EF-сущности расположены в `Models/Bom`, DTO — в `DTOs/Bom`, логика — в `Services/Bom`,
контроллеры спецификаций и заказов — в `Controllers`, конфигурация EF — в `Data`.
`Bom/Expressions.cs` содержит интерпретатор. Сохранённая спецификация закрывается
флагом `IsFinalized`; триггеры запрещают последующее изменение её строк.

API с префиксом `/api/bom`: `/products/{id}` (GET/PUT), `/products/{id}/history`,
`/modifications`, `/variants`, `/preview`, `/variants/{id}/tree`,
`/variants/{id}/totals`, `/orders`, `/orders/{id}`, `/orders/{id}/totals`.
Шаблон принимает `expectedRevisionId`, заказ — `expectedUpdateToken`.
`SpecWrite.Parameters` позволяет явно задать ограничения/подмножества перечислений;
без него сохраняются прежние ограничения и добавляются новые параметры каталога.
SQL-операции: `register_change`, `create_modification`, `bom_effective_positions`,
`find_bom`, `calc_bom`, `calc_order_bom`. Формат запросов доступен в Swagger.

Миграция `SimplifyBom` добавлена после прежних миграций без их изменения.
Последующая `FixBomTreeResultTypes` уточняет текстовые типы результата `find_bom`,
сохраняя таблицы и данные. Для
заполненной БД она требует подтверждённого исходного архива, переносит шаблоны и
зафиксированные деревья и сравнивает их в той же транзакции. При несовпадении
переход откатывается. Откат через Down не восстанавливает старую историю заказов:
для анализа/возврата используется проверенный архив в отдельной БД. Основную БД
автоматически не обновляйте.

Проверки выполняются только на одноразовой БД и отдельном API:

```bash
psql -v ON_ERROR_STOP=1 -f tests/bom_simple.sql
SMARTHOME_TEST_API=http://127.0.0.1:11556/api python3 tests/api_bom.py --allow-test-writes --fixture
```

API-проверки охватывают ПР1–3, вложенную конфигурацию, формулы, модификации,
повторные позиции, диапазоны, даты, enum-подмножества, циклы, конкурентное сохранение
и заказы. `tests/bom_persistence.py` сравнивает сохранённые суммы/деревья через SQL и
API. Ручной сценарий — `tests/gui_bom.md`. Старые SQL-тесты нормализации и переноса
позиций заказов сохраняются для проверки исторических миграций на соответствующей
старой схеме; для текущей модели используется `tests/bom_simple.sql`.

Текущий статус реализации и фактические результаты прогонов следует проверять
по журналам: успешная сборка сама по себе не подтверждает SQL-переход и сохранность данных.

## Маршрутная технология изготовления

Раздел «Маршруты» хранит самостоятельные процессы, типовые шаблоны и их применения.
В разделе «Маршруты» раскройте «Подразделения и рабочие центры», чтобы создать
подразделение (название и тип), затем центр (название, тип и подразделение).
Новые записи сразу доступны в выборе центра операции, несохранённый маршрут
сохраняет введённые поля. Типы добавляются конечными классами в ветвях
«Типы подразделений» и «Типы рабочих центров» классификатора. Имена подразделений
должны различаться, имена центров — различаться в пределах подразделения.
Краткие подсказки рядом с полями поясняют время подготовки, время на единицу,
нормы входов, параметр процесса, справочники и количество для расчёта.

В карточке изделия указывается закупочная цена за текущую единицу. Пустая цена
означает отсутствие данных, 0 ₽ является заданной ценой. Перед сменой единицы цену
нужно очистить. Старые запросы создания и перемещения сохраняют прежний контракт.

Модель позиции `TechStep` имеет два вида: закупка и производство. Закупка ссылается
на материал каталога и его цену. Производство описывает состояние изделия после
операции, рабочий центр, профессию, квалификацию, оснастку и нормы времени. Две
операции над одним изделием представлены двумя позициями. Вход `TechInput`
соединяет результат источника с потребляющей операцией. Норма равна количеству
входа, делённому на базовый выпуск. Вместо количества может использоваться один
числовой параметр настройки.

ER-связи пяти таблиц:

- `department` → `class_node`; `work_center` → `department` и `class_node`.
- `tech_step` → `product`, `measure_unit`, классы операции и профессии,
  `work_center`, значение перечисления квалификации.
- `tech_input` → две позиции `tech_step` и необязательный `parameter_definition`.
- `tech_route_setting` → изделие, необязательное фиксированное исполнение
  `bom_revision`, итоговая позиция и необязательный числовой параметр.

Применения шаблона хранят собственные значения параметра и общую ссылку на итог.
Шаги и связи не копируются. В применении редактируется только значение параметра.
Структура меняется через исходный шаблон. Для самостоятельной структуры создайте
новый маршрут. При добавлении итоговой операции в шаблон его применения продолжают
ссылаться на обновлённый граф. Вложенные изготовленные узлы подключаются через
итоговые позиции сохранённых маршрутов и редактируются в исходном маршруте.

Все расчёты выполняет PostgreSQL в едином контексте изделия и настройки:

| Функция | Аргументы | Результат |
|---|---|---|
| `find_tm` | изделие, партия, настройка | Все пути графа, уровни, позиции, состояния и требуемый выпуск |
| `mr_q` | операция, выпуск операции, настройка | Нормы и расход непосредственных входов |
| `sum_mr` | изделие, партия, настройка | Свод закупных материалов, цены и стоимость |
| `tr_to` | изделие, партия, настройка | Выпуск, минуты и стоимость каждой операции с профессией |

Подготовка учитывается один раз на производственную позицию после суммирования
выпуска по всем ветвям. Прямая себестоимость равна материалам плюс труд. Цена
изготовленного вложенного узла не прибавляется. При отсутствии цены интерфейс
показывает название материала, количества и труд, но оставляет итог неопределённым.
`mr_q` использует введённое количество именно как выпуск выбранной операции.
Остальные функции рассчитывают партию конечного изделия.

API: `GET/POST /api/routes`, `GET/PUT /api/routes/{id}`,
`POST /api/routes/{id}/apply`, `GET /api/routes/lookups`,
`GET /api/routes/{id}/calculate?quantity=10&operationId=…`.
Создание справочников: `POST /api/routes/departments` с `name`, `typeId`;
`POST /api/routes/work-centers` с `name`, `typeId`, `departmentId`. Типы и записи
возвращаются через `/api/routes/lookups`.
Цена: `PUT /api/products/{id}/price` с `{ "purchasePrice": 40 }` или `null`.
Сохранение графа выполняется одной транзакцией, расчёт читает согласованный снимок.
Справочные операции и профессии размещены в служебных ветвях классификатора,
которые нельзя выбирать для изделия. Персональный учёт работников не ведётся.

Для развёртывания применяется новая миграция `AddManufacturingRoutes` после
`FixBomTreeResultTypes`. Она исполняет встроенный `Sql/routes.sql`. Предварительно
выполнять этот SQL в той же БД не нужно. Старые миграции сохранены. Миграция создаёт
справочные значения подразделения, центра, операции, профессии и квалификации,
но не назначает цены существующим изделиям. Откат с удалением данных через `Down`
не поддерживается: для возврата используйте согласованную резервную копию отдельно.

Проверочный запуск направляйте только на новую одноразовую PostgreSQL БД:

```bash
ConnectionStrings__DefaultConnection='Host=127.0.0.1;Port=55480;Database=NEW_DISPOSABLE_DB;Username=postgres;Password=postgres' dotnet ef database update --project SmartHome
ConnectionStrings__DefaultConnection='Host=127.0.0.1;Port=55480;Database=NEW_DISPOSABLE_DB;Username=postgres;Password=postgres' ASPNETCORE_URLS=http://127.0.0.1:12556 dotnet run --project SmartHome --no-launch-profile
```

Для React используйте отдельный Vite-порт и proxy `/api` на этот API. Проверки
`tests/routes_api.py` и `tests/routes.sql` рассчитаны на одноразовую копию учебных

### Учебный пример маршрута

После миграций можно выполнить `SmartHome/Sql/route_example.sql` через
`psql -v ON_ERROR_STOP=1` на выбранной учебной БД. Скрипт требует существующие
изделия с кодами `smart-home-kit`, `signal-cable`, `mounting-fastener` и
фиксированное исполнение «Проводной — 2 датчика». Он добавляет шаблон
«Типовой монтаж комплекта» и применения «Проводной 1 м» / «Проводной 2 м»,
назначает учебные цены 40 ₽/м и 12 ₽/шт. только при отсутствии цены.
При конфликте цен или неполном примере транзакция отменяется. Повторный запуск
не создаёт дубликаты и проверяет контрольные затраты 510 / 3 813 / 550 ₽.
Существующие спецификации и заказы не изменяются.
